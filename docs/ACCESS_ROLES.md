# 资源访问用户组

人员和 Agent 可以加入多个用户组，继承用户组的资源授权；原有直接授权继续有效。用户组只授予资源访问能力，不授予管理后台权限。

界面统一使用“用户组”。已有配置和 API 的 `roles`、`role_id`、`role-memberships` 字段继续兼容，导入导出无需迁移。

## 配置流程

1. 在 **资源管理 → 资源名称 / 查看详情 → 添加资源账号** 保存真实登录账号，检查连接与远端权限，再启用账号。SSH 账号需要核验指定算法的主机指纹。账号密码、私钥仍由后端加密托管。
2. 在 **用户组管理** 创建用户组，填写名称、说明和启用状态。
3. 打开用户组详情，在 **用户组成员** 批量选择人员或 Agent，按需设置开始、到期时间。系统账号详情也能批量分配或移除用户组。
4. 在用户组详情点击 **添加资源授权**，选择资源、普通或高权限账号、允许操作、有效期及执行限制。可同时选择其他资源；每个资源独立选择账号和动作，整批保存或整批回滚。
5. 在系统账号详情点击 **查看最终可用权限**。资源账号列表会反查用户组及其生效成员；用户组详情提供分页变更记录。
6. 人员进入 `/#access-user`（有部署前缀时为 `/deebee/#access-user`），选择资源及账号/权限来源，再查询、执行或打开交互会话。Agent 继续使用 MCP/REST。

分类和标签用于筛选，新增资源不会仅因为标签相同就自动继承权限。每个授权对象对每个资源保留一份授权，可绑定一个普通账号和一个高权限账号；同一人通过不同用户组可以获得多个候选账号。

## 用户组与远端账号

用户组通过每条资源授权绑定资源上的真实账号。例如“生产巡检”用户组可以绑定主机 A 的 `inspect` 和数据库 B 的 `report_ro`。用户组名称无需等于主机用户名，凭据不保存在用户组中。

本版采用托管账号映射。个人同名账号和自动创建远端账号属于后续账号供应能力，未随本次用户组功能实现。分配用户组不会创建 Linux 用户、配置 sudo 或修改数据库权限。

只读能力由实际远端权限和执行方式共同保证。服务器巡检使用固定 `ssh.inspect`；`ssh.exec` 和 `ssh:connect` 都可能修改账号有权写入的内容。交互终端与远程桌面必须单独授予 `ssh:connect` / `rdp:connect`，旧授权和旧 API Key 不会自动获得这两个新权限。

SSH 资源启用审批规则后，普通系统账号通过 `ssh.exec` 逐条提交命令，原始交互终端由服务端关闭，避免绕过审核。MySQL/PostgreSQL 变更和危险 SSH 命令默认进入管理员审批；通过不会扩大用户组或凭据原有权限。详见 [操作审批说明](OPERATION_APPROVALS.md)。

RDP 通过 guacd 连接，配置 Windows 域和安全模式。TLS/NLA 不跳过证书验证；自签名证书需在 guacd 信任库中预先配置。RDP 的真实测试不能证明 Windows 账号只读，因此本版仅允许核验并人工确认后的高权限账号类别。原工作台中关闭证书验证的 RDP 连接会保持不可发布状态。

## 授权判定

每次访问必须完整匹配一条授权路径：有效系统账号、有效身份凭据/绑定、有效用户组及成员关系、有效资源授权、有效且已核验的资源账号，以及对应动作、凭据 scopes 和资源白名单。

多个用户组可增加候选授权，但不能混合一条授权的动作与另一条授权的账号、额度或特权开关。请求、资源及所选授权的执行限制取更严格值。高权限依旧要求显式 `mode: privileged`、`allow_privileged` 和 `privilege:use`；sudo 仍须显式请求。

`resources.list` / `resources.get` / REST 资源发现的每个 `access_modes` 项新增：

- `access_option_id`：绑定系统账号、身份绑定、资源、账号、授权、用户组和成员关系版本的服务端选择器。
- `grant_id`、`role_id`、`role_name`、`source`：权限来源，直接授权的 `source` 为 `direct`。
- `expires_at`、`limits`：本次凭据和完整授权路径的有效期及限制。

执行及数据库结构查询可以传 `access_option_id`。有多个符合本次动作的候选授权但未选择时，返回 `ACCESS_SELECTION_REQUIRED`；唯一候选继续兼容旧请求。所选路径修改、过期或被撤销后，旧选择器失效，不会自动换用其他用户组。客户端应重新发现后让使用者选择。

人员交互使用 `POST /api/v1/sessions`，再建立返回的会话 ID 对应的 WebSocket。需要人员浏览器 Cookie、写请求 CSRF、同源 Origin、相同登录身份和未使用的 30 秒会话 ID；会话 ID 本身不能代替身份凭据。人员不会获得原管理员工作台 Token，也不能调用管理 API。SSH、RDP 复用现有录像；数据库查询、写入和结构读取使用受限执行链路。

## 撤权与审计

移除成员、停用用户组/授权/账号或到期后，新请求立即拒绝。排队执行在接触目标前重新校验；运行任务通过变更事件及每秒检查发起取消；交互会话每 0.5 秒检查授权，在输入转发前再检查，登录会话最多每秒重新验证一次。远端已经完成的修改不能回滚，SSH 子进程或数据库提交存在取消竞争时继续标记 `unknown`，需核实远端状态。

执行记录保存用户组名称、用户组 ID、授权 ID、成员关系 ID和实际远端账号。删除用户组会停用并保留用户组、成员、授权的内部历史记录，管理列表隐藏这些记录；历史执行与审计继续保留。复制用户组只复制用户组定义和停用的资源授权，不复制成员，也不自动启用新用户组。

## 管理 API 与升级

新增 `/api/admin/v1/roles`、`/role-memberships` 的列表、创建、编辑接口，以及：

- `POST /roles/{id}/members`：按用户组批量分配或停用成员。
- `POST /role-memberships/batch`：带成员版本的跨用户组批量配置。
- `POST /roles/{id}/clone`、`DELETE /roles/{id}`：复制和带名称确认的删除。
- `GET /roles/{id}/activities`：按用户组及关联记录查询，支持 `before` 分页。
- `POST /access-grants/batch`：原子创建一批明确的资源授权。

新建用户组授权省略 `actions` 时仅允许查看资源，执行动作需明确配置；旧直接授权的默认值保持兼容。资源授权新增可选 `role_id`、`starts_at`，`principal_id` 和 `role_id` 必须且只能填写一个。旧 `principal_id` 授权继续有效。数据库启动时迁移唯一索引，不自动给已有人员分配用户组，也不扩大已有授权。配置导出升级为版本 2，包含用户组和成员；版本 1 仍可导入。预览回滚、不导入秘密、乐观版本检查及原子回滚保持生效。

逐项验收见 [用户组功能验收记录](ACCESS_ROLES_QA.md)。

## 环境与资源展示

资源可以选择生产（prod）、验收（uat）、预发布（staging）、测试（test）、开发（dev），也可以填写自定义环境。已有自定义环境会出现在其他资源的编辑选项中；清空后归入“未分配环境”。环境名称保持原样存储，常见环境补充中文说明。分组数量统计全部资源，可继续组合类型、项目组、标签、状态和搜索条件。

资源卡片和表格不展示连接账号。点击资源名称或详情可管理账号与授权；人员侧在选中资源后的操作区选择可用账号。九类已识别资源均使用随应用打包的 Devicon 产品图标，RDP 显示 Windows 图标。图标来源和许可证见 `src/assets/resource-icons/README.md`。
